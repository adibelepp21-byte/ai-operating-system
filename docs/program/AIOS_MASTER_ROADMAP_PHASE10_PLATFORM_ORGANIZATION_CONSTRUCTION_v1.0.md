0. PURPOSE
This document defines the master Product Requirements and execution roadmap for the construction period covering:
	1.	Master Program Phase 10 — Department Ecosystem
	2.	Platform Organization Construction Track — PD-01–PD-10
	3.	Their reconciliation, integration, operationalization, verification, and post-execution discovery.
This document is intentionally designed as a construction roadmap, not as a serial list of micro-Acts.
It defines what successful construction must achieve, the work-package surfaces that must be covered, the invariants that must not be violated, the execution semantics, and the exhaustion gate.
Claude Code is responsible for discovering the concrete work graph, selecting the appropriate implementation order, making delegated technical decisions, executing authorized work, verifying results, and re-discovering the system after meaningful construction.
Canonical distinction
> **Phase 10 ≠ Platform Organization Construction.**
Phase 10 is a Main Capability Roadmap phase: Department Ecosystem.
PD-01–PD-10 form the Platform Organization Construction Track, a cross-phase organizational/platform architecture layer. They are not Phase 14 and do not replace Phase 1–13.
The two surfaces may be constructed and integrated together where dependencies require it, but their state, completion, evidence, and reporting remain distinct.

1. SOURCE AND ARCHITECTURAL BASIS
The AIOS Platform Encyclopedia establishes two roadmap layers:
	●	Main Capability Roadmap: Phase 1–13
	●	Platform Organization Construction Track: PD-01–PD-10
The Platform Organization goal is to make, for each platform domain:
> Clear Identity → Clear Authority → Clear Ownership → Clear Capability → Clear Architecture → Clear Operation → Measurable Performance → Controlled Lifecycle → Controlled Integration → Controlled Evolution.
PD-01 is the Reference Implementation. Its validated pattern is reusable across PD-02–PD-10, while domain content must remain domain-specific.
Phase 10 remains:
> **Department Ecosystem**
and is downstream of Phase 9 Workflow Ecosystem and upstream of Phase 11 Autonomous Organization.
This roadmap therefore does not redefine the Master Program.

2. PRODUCT / PROGRAM OBJECTIVE
2.1 Primary objective
Advance AIOS from its current construction state toward the furthest legitimately achievable intended state for Phase 10 and the Platform Organization construction surface, using all available canonical sources, existing implementation, architecture, governance, evidence, and delegated execution authority.
The execution objective is:
> **DISCOVER → CLASSIFY → DECIDE → BUILD/FIX/INTEGRATE → VERIFY → RE-DISCOVER → CONTINUE**
until the actual executable construction surface is exhausted or every remaining blocker has been correctly escalated or classified as a source gap.
2.2 Desired outcome
AIOS should emerge with:
	●	a coherent Phase 10 Department Ecosystem;
	●	a coherent Platform Organization construction state;
	●	PD-01 functioning as the validated reference pattern;
	●	PD-02–PD-10 constructed or reconciled according to their actual domain requirements;
	●	organizational and capability boundaries explicitly connected;
	●	existing AIOS implementation connected to the organizational source layer;
	●	cross-surface contracts and ownership made explicit;
	●	unresolved conflicts surfaced rather than silently absorbed;
	●	implementation/evidence/verification lineage preserved;
	●	operationalization demonstrated where legitimately possible;
	●	no falsely claimed completion.

3. NON-NEGOTIABLE INVARIANTS
INV-01 — Phase 10 ≠ Platform Organization
Never represent:
PD-01–PD-10 = Phase 10
and never represent:
PD-01–PD-10 = Phase 14
Phase 10 and Platform Organization are separate but integrated dimensions.
INV-02 — Phase 1–13 remains the Main Capability Roadmap
The construction track must not replace, renumber, collapse, or redefine Phase 1–13.
INV-03 — PD-01 is Reference Implementation
PD-01 supplies reusable construction/documentation/organization patterns.
PD-02–PD-10 must adapt the pattern to their own domain and must not inherit PD-01 domain content by mechanical copying.
INV-04 — No Endless Reading
Reading is not a completion mechanism.
Source reading is justified only when it:
	●	resolves an active ambiguity;
	●	establishes authority;
	●	provides missing evidence;
	●	reveals actionable construction;
	●	protects against architectural drift;
	●	is required for verification.
Once sufficient evidence exists, execution must proceed.
INV-05 — Discovery Must Convert to Action Where Possible
A discovery that is legitimately actionable must be classified and acted upon.
The minimum action classes are:
	●	BUILD — create missing capability/artifact/implementation;
	●	FIX — repair an incorrect, incomplete, inconsistent, or broken state;
	●	INTEGRATE — connect existing surfaces/contracts/ownership/evidence;
	●	VERIFY — test or prove an already-constructed state;
	●	ESCALATE — authority or dependency requires a reserved decision;
	●	SOURCE-GAP — source/evidence is insufficient to legitimately proceed.
A finding must not become an endless analysis loop.
INV-06 — No Micro-Act for Delegated Technical Decisions
Claude Code must not create or request a new micro-Act merely to obtain permission for a technical, architectural, engineering, documentation, implementation, or verification decision that is already within delegated authority.
Delegated authority must be used.
Reserved authority must be escalated.
INV-07 — No Silent Authority Expansion
Autonomy does not authorize:
	●	constitutional changes;
	●	changes to Founder Reserved Authority;
	●	unauthorized strategic commitments;
	●	silent changes to canonical architecture;
	●	irreversible external commitments outside delegated scope.
INV-08 — Existing Implementation Is Evidence, Not Automatically Canonical
Existing code/artifacts must be inspected and classified as:
	●	canonical;
	●	implementation-aligned;
	●	implementation-drift;
	●	legacy;
	●	experimental;
	●	incomplete;
	●	obsolete;
	●	unknown.
Do not rewrite working implementation merely to make it cosmetically conform.
INV-09 — Verify Construction, Then Re-discover
A meaningful construction wave must be followed by verification and fresh discovery.
The system state after construction is the input to the next construction wave.
INV-10 — Completion Is Not Report Generation
A return package is evidence of completion only when the actual exhaustion gate has passed.
A clean report, successful test, or completed checklist does not by itself establish program completion.

4. EXECUTION SEMANTICS
Claude Code shall operate as an autonomous construction executor inside the delegated authority envelope.
The intended behavior is:
```text CURRENT STATE      ↓ DISCOVER      ↓ UNDERSTAND / CLASSIFY      ↓ AUTHORITY CHECK      ├── SUFFICIENT → DECIDE      │                  ↓      │               EXECUTE      │                  ↓      │               VERIFY      │                  ↓      │             RE-DISCOVER      │      └── INSUFFICIENT → ESCALATE / SOURCE-GAP                            ↓                      CONTINUE ELSEWHERE ```
Construction-first rule
If an actionable gap can be legitimately closed:
> **BUILD / FIX / INTEGRATE it.**
Do not substitute a new analysis cycle for available construction.
Parallelization rule
Claude Code may parallelize work where dependency analysis proves that doing so is safe.
The roadmap’s WP order is a control structure, not a requirement to execute every sub-item serially.

6. ACTUAL EXHAUSTION GATE
The program may be declared construction-exhausted only if all of the following are true.
EXH-01 — Fresh discovery completed
A genuine post-execution discovery has been performed.
EXH-02 — Construction graph generated from current state
The remaining work is derived from the current system, not copied from an earlier checklist.
EXH-03 — No authorized actionable work remains
There is no remaining work that is simultaneously:
	●	legitimately in scope;
	●	supported by sufficient source/evidence;
	●	authorized under the current authority envelope;
	●	technically actionable;
	●	not already completed.
EXH-04 — Remaining blockers classified
Every remaining unresolved item is classified as one of:
	●	Founder Reserved Authority;
	●	Architect Reserved Authority;
	●	external dependency;
	●	source gap;
	●	evidence gap;
	●	intentional future-phase work;

The system must not claim:
	●	all AIOS is complete;

	●	all possible work is complete;
	●	all ambiguity has disappeared.

7. STOPPING SEMANTICS
Claude Code may stop only under one of the following legitimate conditions:
STOP-A — Actual exhaustion
No authorized actionable construction remains after fresh discovery.
STOP-B — Reserved authority blocker
Remaining work requires Founder or other explicitly reserved authority.
Claude must report the blocker and continue all independent work that does not depend on it.
STOP-C — Source gap
A required decision or implementation cannot be legitimately made because authoritative source/evidence is absent.
Claude must record the exact source gap and avoid invention.
STOP-D — External dependency
Execution is blocked by a real external dependency outside the delegated boundary.
STOP-E — Safety / integrity boundary
Continuing would violate constitutional, architectural, security, or governance constraints.
Invalid stopping reasons
The following are not sufficient stopping reasons:
	●	“the checklist is complete”;
	●	“the documents are written”;
	●	“tests passed”;
	●	“I found no more issues in the previous inventory”;
	●	“the repository is clean”;
	●	“the previous cycle declared exhaustion”;
	●	“the roadmap ended”.

8. SOURCE-GAP PROTOCOL
When source evidence is insufficient:
	1.	identify the exact missing source;
	2.	state why it matters;
	3.	determine whether another authoritative source resolves it;
	4.	search only as much as necessary;
	5.	do not invent a canonical decision;
	6.	classify as SOURCE-GAP;
	7.	continue unrelated authorized construction.
A source gap is not permission to stop the entire program.
￼
9. ESCALATION PROTOCOL
Escalation must be:
	●	specific;
	●	evidence-backed;
	●	minimal;
	●	decision-oriented.
Claude must not escalate:
> “What should I do next?”
when the answer can be derived from delegated authority and repository evidence.
Claude should escalate:
> “Decision X requires Founder Reserved Authority because source Y assigns this authority exclusively to Founder; option A and B are available, with consequences C and D.”
After escalation, Claude must continue all work that does not depend on the unresolved decision.
