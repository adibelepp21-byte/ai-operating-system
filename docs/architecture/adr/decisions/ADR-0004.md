# ADR-0004

- **Status:** Approved

- **Date:** 2026-07-16

## Context

The Canonical Domain Model defines Workflow as an entity (§2), categorizes it under Execution (§3), and includes it in five ratified relationships (§4: Agent Definition specifies Workflow; Agent Instance follows Workflow; Workflow contains Skill; Workflow invokes Agent Instance). However, Workflow is absent from both the Ownership Rules table (§5) and the Lifecycle Rules table (§6) — the only Execution-layer entity missing from both. This is a structural incompleteness in ratified text, not an interpretive ambiguity: no owner or lifecycle model for Workflow is stated anywhere. Existing text offers no single dictated answer, since Workflow's Execution-layer peers span three distinct ownership treatments (Department-exclusive for Agent Definition; centrally-owned for Skill/Tool/Runtime; not-owned/transient for Agent Instance).

## Decision

Workflow is owned centrally, per Domain Model §5, joining Skill, Tool, and Runtime in that ownership category.

**Classification rationale:** Workflow is, per its own definition in Domain Model §2, a composition of Skills (and possibly Agent Instance invocations) accomplishing a multi-step outcome — an Execution-layer coordination primitive, not a business-domain contract. This places it architecturally closer to Skill, Tool, and Runtime, each a reusable, composable unit centrally available for use across Departments, than to Capability, whose §2 definition centers on being a named, outcome-oriented contract owned by a single Department, independent of how it is composed or implemented. Central ownership follows from this classification, not merely from a wish to avoid cross-Department complexity — avoiding that complexity prematurely is a consequence of the classification, not its basis.

This classification also distinguishes Workflow from Agent Definition, the entity to which Workflow is most directly related via the specifies relationship (§4). Agent Definition is a Department-owned artifact (§5) that defines a class of Agent's identity, purpose, constraints, and governance boundary — a stable specification accountable to a single Department, per Domain Model §2 and §6. Workflow, by contrast, is an Execution-layer coordination primitive: it defines the orchestration and composition of Skills, and possibly Agent Instance invocations, into a multi-step outcome, independent of which Department's Agent Definition happens to specify it. That Agent Definition specifies Workflow (§4) does not imply shared ownership between the two entities — specification and ownership are separate concerns in the Domain Model, exactly as Agent Definition's specifies relationship to Skill does not make Skill Department-owned either. Workflow's central ownership therefore follows from its own Execution-layer coordination role, not from any Department's accountability for the Agent Definitions that happen to reference it.

Workflow's Lifecycle Rules entry (§6) is defined as follows:

- Versioned independently.
- Evolved through governed revisions.
- Compatibility boundaries preserved where applicable.
- Behavioral drift documented at change time.

This lifecycle treatment is framed as a **shared governance pattern applied consistently across centrally-owned Execution-layer entities** — the category Workflow now joins alongside Skill, Tool, and Runtime — not as a claim that Workflow is identical to, or interchangeable with, Skill or Tool. Each centrally-owned entity retains its own distinct architectural identity (§2); only the governance treatment of change over time is shared.

**Relationship to ADR-0005:** This same shared lifecycle governance pattern is being independently proposed for Runtime under ADR-0005. The two ADRs are designed to establish this pattern jointly for the centrally-owned Execution-layer category, not to duplicate it independently of one another. Should ADR-0005 be approved first, this ADR's Lifecycle Rules content for Workflow should be understood as adopting the pattern ADR-0005 establishes, rather than independently asserting it a second time; the reverse holds if this ADR is approved first. Neither ADR's approval is assumed or inferred by this cross-reference.

## Alternatives Considered

1. **Workflow owned by Department** (parallel to Capability, Agent Definition). *Benefits:* consistent with Department-level accountability for multi-step business outcomes; extends an existing, well-precedented storage pattern (Organization Framework). *Risks:* creates an ownership asymmetry with the centrally-owned Skills a Workflow contains; surfaces a new, previously unaddressed cross-Department invocation question (a Department-X-owned Workflow invoking an Agent Instance whose Agent Definition belongs to Department Y). *Reason rejected:* the Architect's rationale explicitly identifies avoiding this cross-Department governance complexity, prematurely, as a goal of this decision.
2. **Workflow has another ownership model** (contextual, inherited, or hybrid). *Benefits:* could more precisely capture Workflow's compositional relationship to whatever specifies or contains it. *Risks:* unprecedented relative to every other entity in §5, each of which has a fixed, single, entity-type-level ownership answer, not a conditional one; no existing storage or reference convention accommodates it; highest design burden of any option. *Reason rejected:* not selected by the Architect; no rationale for this option was supplied.

## Consequences

### Positive Consequences
- Fully closes the structural gap in ratified text — Workflow is now present in §2, §3, §4, §5, and §6 alike.
- Avoids introducing Department-vs-Department invocation governance questions at this time, consistent with the Architect's stated rationale.
- Preserves ownership-category symmetry between Workflow and the Skills it contains (§4: Workflow contains Skill), since both are centrally owned.
- Establishes lifecycle governance through a shared pattern rather than an entity-specific one, avoiding any implication that Workflow, Skill, and Tool are functionally interchangeable.

### Negative Consequences
- Ties Workflow's eventual storage/documentation convention to the still-undesigned central-storage convention question already identified for Skill, Tool, and Runtime — a dependency outside this ADR's scope.
- Leaves the cross-Department invocation question theoretically open should Workflow's ownership model ever be revisited.

### Future Implications
- A future central storage convention (Framework-level, not yet designed) will need to account for Workflow alongside Skill, Tool, and Runtime.
- Agent Definition Framework §12's existing treatment of Skill and Workflow as symmetric, name-only references (neither having its own Framework yet) remains accurate and undisturbed by this decision.
- A future Workflow Framework, once designed, should document the shared governance pattern's specific application to Workflow without restating it as though newly invented.

## Domain Model Impact

- **Entities affected:** Workflow (directly); Skill (indirectly, via the containment relationship, ownership-category symmetry preserved); Agent Definition (indirectly, via the specifies relationship).
- **Relationships affected:** None of §4's five Workflow relationships change in content.
- **Ownership impact:** §5 gains Workflow under the existing "owned centrally" category (proposed table treatment: extend the existing "Skill / Tool / Runtime" row to "Skill / Tool / Runtime / Workflow," subject to Architect confirmation of table formatting).
- **Lifecycle impact:** §6 gains a new Workflow row: versioned independently; evolved through governed revisions; compatibility boundaries preserved where applicable; behavioral drift documented at change time.
- **Invariant impact — evaluated, not invented:** No new invariant is proposed. The existing centrally-owned entities (Skill, Tool) carry no dedicated ownership-uniqueness or lifecycle-specific invariant in §7 beyond Tool-specific invariant 12 (external-dependency boundary, not applicable here). Extending Workflow into the same ownership and lifecycle category with no existing invariant to match argues against inventing one here. This conclusion should be confirmed by the Architect, not treated as final.

## Framework Impact

### Required Future Changes
- None mandated directly by this ADR.

### Optional Future Work
- A central storage/documentation convention for centrally-owned Execution-layer entities (Skill, Tool, Runtime, Workflow) — not designed here, previously identified as a separate Framework-level gap.
- A future Workflow Framework, now unblocked with respect to the Domain Model content it would need to cite — still contingent on the central storage convention above.

### Unaffected Frameworks
- ADR Framework — unaffected.
- Organization Framework's existing Department-nested convention for Capability and Agent Definition — unaffected; Workflow does not join that pattern under this decision.

## Non-Goals

This ADR does not:
- Resolve cross-Department Agent Definition invocation rules.
- Modify Agent Definition ownership.
- Modify Capability ownership.
- Define Workflow Framework storage conventions.
- Define central storage implementation details.
- Create a Workflow Framework.
- Resolve the cross-Department Workflow invocation question implicitly avoided by choosing central ownership.
- Claim that Workflow is identical to, or functionally interchangeable with, Skill or Tool; only the lifecycle governance pattern is shared, not entity identity.
