## Context

Domain Model §9 (Explicit Non-Goals) states that Session is represented as a scope attribute on Memory *and* Trace. §2.1 (Trace — Required Contents), the closed list of what every Trace record must contain, does not include any scope or session field. These two ratified passages are in tension: one asserts Trace carries scope, the other's operative, exhaustive list does not name it. Only the Domain Model's own amendment process can reconcile which governs.

## Decision

Option C reconciliation is selected: the apparent tension is resolved through clarifying language rather than by adding or removing a substantive field.

**Clarified formulation:** Where Session/scope information exists through captured scoped entities (such as Memory), Trace preserves that contextual information through existing content-capture rules (§6.1).

This formulation is deliberately narrower than an earlier working phrasing ("Trace reflects Session/scope indirectly through Memory"). It does not imply that Memory is mandatory for every Trace record, or that every Trace record necessarily carries session/scope context. It states only that *when* a Trace record does capture content from a scoped entity such as Memory, whatever scope/session context that entity carries is preserved as part of the already-required content-capture (§2.1's Memory-consumed field), not lost and not requiring separate declaration.

No new field is added to §2.1's required-contents list.

**Reconciliation mechanism:** This tension is reconciled through this ADR's own interpretive clarification, exercised under Constitution §3.4/§5's ADR-based Domain Model amendment mechanism — not through adding or removing any field in §2.1's required-contents list, which remains textually unchanged and unamended by this ADR.

**§9 textual amendment:** §2.1 requires no textual change, since its existing required-contents list was already accurate and is not expanded by this ADR. §9, however, requires a textual amendment: its current wording asserts a scope attribute on Trace without the conditional, indirect qualification this ADR establishes, and leaving it unamended would preserve the very inconsistency this ADR exists to resolve. The proposed amended §9 wording is: Session is not treated as a first-class entity; it is represented as a scope attribute on Memory, and reflected within Trace only indirectly and conditionally — through whatever scoped content Trace has already captured from Memory at write-time, per §6.1 — not as an independent, separately-declared Trace field. This amendment is a textual clarification of existing §9 content, not a new claim; it does not add, remove, or redefine any entity, relationship, or invariant. Applying this text to the Canonical Domain Model document itself is a separate, future, explicitly-authorized step and is not performed by this ADR draft.

## Alternatives Considered

1. **Add a Session/scope field to Trace's §2.1 required contents (Option A).** *Benefits:* gives a future Trace Framework's validation model one more explicit, directly checkable field; strengthens completeness-validation. *Risks:* expands Trace's mandatory-contents contract, with direct downstream design and validation obligations, and would require every Trace record to carry scope information regardless of whether a scoped entity was actually involved in the action. *Reason rejected:* not selected by the Architect; the decision explicitly states the Trace contract should not be expanded.
2. **Remove the Trace reference from §9's Non-Goals bullet (Option B).** *Benefits:* simplest possible textual correction; resolves the inconsistency by narrowing rather than expanding. *Risks:* removes a real design capability — a future Trace Framework would be unable to support session-correlation directly from an isolated Trace record, requiring cross-referencing cited Memory content instead. *Reason rejected:* not selected by the Architect.

## Consequences

### Positive Consequences
- Resolves the internal §2.1/§9 inconsistency without expanding Trace's mandatory-contents contract.
- Preserves the practical capability of session-correlation where a scoped entity was actually captured, without falsely implying every Trace record involves one.
- Requires no new invariant text, since no new field is added.
- More precise than the earlier "through Memory" phrasing — avoids overstating Memory's role in every Trace record.

### Negative Consequences
- Requires an interpretive judgment about what §9's original language was intended to mean — a smaller textual footprint than Options A or B, but not a purely mechanical fix either.
- The conditional phrasing ("where... exists") is slightly more complex to state precisely than a flat assertion, though this is accepted as the cost of accuracy.

### Future Implications
- A future Trace Framework should document that session/scope correlation is conditionally available — derived transitively through captured scoped-entity content when such content exists — rather than guaranteed on every Trace record. Its validation model must not treat scope/session as universally present.

## Domain Model Impact

- **Entities affected:** Trace (clarified, not expanded). Memory is referenced but not modified — this clarification does not assert that every Trace record consumes or references Memory, only that when it does, scope context is preserved through existing capture rules.
- **Textual amendment scope:** §9 requires a textual amendment (proposed replacement wording stated in Decision, above, pending Architect approval and separate implementation); §2.1 requires no textual change.
- **Relationships affected:** None of §4's Trace relationships change in content.
- **Ownership impact:** Not applicable.
- **Lifecycle impact:** Not applicable — Trace's append-only, immutable lifecycle (§6) is unchanged.
- **Invariant impact:** None. Because no new field is added to §2.1, invariants 4 and 6 (governing Trace's required contents and content-capture behavior) remain accurate as currently written and require no amendment.

## Framework Impact

### Required Future Changes
- None mandated directly by this ADR.

### Optional Future Work
- A future Trace Framework's design should reflect that session/scope is conditionally derivable via captured scoped-entity content (such as Memory) rather than guaranteed via a dedicated Trace field or assumed present on every record.

### Unaffected Frameworks
- Organization Framework — unaffected.
- Agent Definition Framework — unaffected.
- ADR Framework — unaffected.
- A Trace Framework is explicitly not created by this ADR (see Non-Goals).

## Non-Goals

This ADR does not:
- Add any new required field to Trace's §2.1 contents.
- Define a Session identifier format.
- Define a Trace Framework.
- Define Trace storage.
- Define retention policy.
- Modify Memory semantics.
- Expand any Trace invariant.
- Assert that Memory is mandatory for every Trace record.
