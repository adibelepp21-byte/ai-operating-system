# ADR-0003

## Metadata

- **Identifier:** ADR-0003
- **Title:** Establish the Platform Department and its first Capability, Governance Artifact Integrity
- **Status:** Approved
- **Proposer:** AI Systems Engineer
- **Approval Record:** Approved by Architect — see Approval Record
  section, below.

## Context

AIOS's governance foundation — the Engineering Constitution, the
Canonical Domain Model, and the ADR Framework — is complete and has been
exercised twice, through ADR-0001 and ADR-0002, both correcting stale
wording in the Canonical Domain Model. Neither created any Department or
Capability instance. The Organization Framework, established separately,
defines where and how such instances are recorded, but no instance has
existed until now.

The work this ADR formalizes — keeping the Constitution, Domain Model,
and ADR Framework internally consistent and free of duplication — has
already been performed repeatedly throughout AIOS's history without a
named organizational home.

## Problem Statement

Department and Capability exist in the Canonical Domain Model as ratified
entity types, but zero instances exist. AIOS's Spine has no operational
referent, and already-demonstrated governance-maintenance work has no
accountable structure to attach to.

## Decision

Create:

- A Department named **Platform**, responsible for the operational work
  of maintaining, evolving, and safeguarding AIOS's own governance and
  semantic substrate — the artifacts and mechanisms every other future
  Department and Capability will depend on. Platform holds no
  Constitutional Tier authority and no independent Domain Model approval
  authority; it is not a catch-all for future business or product
  Departments' work.
- A Capability named **Governance Artifact Integrity**, owned by
  Platform, defined as: "Maintain the internal consistency and accuracy
  of AIOS's governance artifacts — the Engineering Constitution, the
  Canonical Domain Model, and their subordinate procedural documents —
  so that no artifact diverges from what it describes or duplicates
  another artifact's authoritative content."

Both are recorded per the ratified Organization Framework convention at:

- `docs/architecture/organization/platform/README.md`
- `docs/architecture/organization/platform/capabilities/governance-artifact-integrity.md`

No entry in the Canonical Domain Model document is added, removed, or
altered by this ADR.

**Explicit confirmation of scope:** zero Domain Model entity,
relationship, ownership rule, lifecycle rule, or invariant text changes.
This Decision instantiates already-ratified entity types; it does not
amend their definitions.

**Explicit transient invariant state explanation:** immediately following
this ADR's approval, the Governance Artifact Integrity Capability will
have zero Agent Definitions implementing it. This is the exact condition
the Domain Model's invariant on zero-Agent-Definition Capabilities
identifies as an invalid steady state requiring governance review. This
is an expected, temporary condition, not an oversight: this ADR
deliberately does not create any Agent Definition, since that is
Department-discretion work under existing Domain Model lifecycle rules,
not an architectural-tier decision requiring an ADR. The Platform
Department is expected to create at least one Agent Definition
implementing this Capability promptly following this ADR's approval, as
ordinary follow-up work outside this ADR's scope.

## Alternatives Considered

1. **Create the Department only, defer the Capability.** Rejected —
   leaves an inert Department with nothing to own, likely requiring an
   immediate follow-up ADR to become useful.
2. **Create multiple Capabilities at once.** Rejected — risks
   under-considered scope for any individual Capability; the Domain
   Model's own architectural boundaries favor deliberate, incremental
   growth of the Spine over a large first commitment.
3. **Choose a speculative business-domain Department instead of a
   governance-substrate one.** Rejected — no product or business domain
   has been chosen for AIOS yet; inventing one now would populate the
   Spine with fictional content rather than already-demonstrated work.
4. **Bundle Agent Definition creation into this ADR.** Rejected — Agent
   Definition creation is Department-discretion, Implementation Tier
   work under existing Domain Model rules; it does not require or
   benefit from ADR-level review.

## Consequences

The Platform Department becomes AIOS's first real Spine instance; the
Domain Model's ownership and Agent-Definition invariants gain a real,
checkable subject for the first time rather than holding vacuously. No
Canonical Domain Model document change occurs. No technology, storage,
or tooling decision is introduced. This ADR establishes the first worked
template for future Department and Capability creation decisions under
Constitution §3.4's Department-and-Capability-structure category.

## Validation

- **Authority validation:** Proposer standing is valid under Constitution
  §3.4. Approval authority is the Architect directly. Unlike ADR-0001 and
  ADR-0002, this is not because Department/Capability creation is
  categorically non-delegable — creating a single Department with a
  single Capability does not by itself constitute a cross-Department
  structural change — but because no delegation is currently in force,
  and Constitution §3.2's default places architectural-tier authority
  with the Architect absent one.
- **Boundary validation:** No Constitutional Tier content is touched; no
  technology, language, framework, or infrastructure decision appears;
  delegation limits are not implicated since approval is direct.
- **Contradiction check:** No conflict with ADR-0001 or ADR-0002, the
  only prior Approved ADRs. Both concerned wording corrections to the
  Canonical Domain Model; neither addressed Department or Capability
  creation.
- **Domain Model impact review:** Not mandated by the ADR Framework's
  Validation Model, since this ADR does not affect the Canonical Domain
  Model document. Included for completeness: zero entities,
  relationships, ownership rules, lifecycle rules, or invariants are
  altered by this ADR; existing rules are exercised, not changed.
- **Organization Framework compliance:** The Department and Capability
  names, slugs, and file locations specified in the Decision match the
  ratified Organization Framework convention exactly.
