# ADR-0013

## Metadata

- **Identifier:** ADR-0013
- **Title:** Concrete execution-consumer residency is uniquely determined by the
  boundary permission graph, and is therefore not the E-01 blocker
- **Status:** **Approved** (delegated architecture decision)
- **Decision Owner:** Co-Founder / Delegated Architecture Authority
- **Proposer:** Claude Code / Co-Founder (Construction Phase)
- **Approval Record:** Executed under Founder authorization **DEC-P6-035**,
  which delegates residency resolution and expressly reserves any relaxation of
  the Agent boundary.

This document records a **delegated** architectural-tier decision. It creates no
new authority, decides no Founder-reserved question, and authorizes no
implementation.

---

## 1. Context

`DEC-P6-035` accepted the `ACT-CC-P6-039` finding and asked one question:

> *"Where should the concrete execution consumer required by E-01 legitimately
> live?"*

It authorized **Option B** — relocate outside the Agent boundary — and expressly
did **not** authorize **Option A** (relax Agent conformance) or select **Option
C** (a semantically vacuous realization).

## 2. Method

[A] The question is decidable by exhaustive search, because realizing the
contract has one hard prerequisite: **a concrete consumer must import
`ExecutionConsumer` from `runtime.execution.consumer`.** Any residency must
therefore sit in a package permitted to import from `runtime`.

## 3. Evidence

[E] **Only one boundary in the entire Native Core may import from `runtime`.**
Across all eleven boundaries, exactly one `PERMITTED_BOUNDARIES` declaration
names it:

```
agent      PERMITTED_BOUNDARIES = frozenset({"runtime"})       ← the only one
runtime    PERMITTED_BOUNDARIES = frozenset({"infrastructure", "knowledge"})
capability · governance · infrastructure · knowledge · memory ·
optimization · skill · trace · workflow — none names runtime
```

[E] **The Runtime package may not import the consumer contract at all.**
`test_runtime_never_learns_of_a_consumer` collects every Runtime module
importing `ExecutionConsumer` and asserts `assertEqual([], importers)` — an
equality on the empty list. Its stated reason: *"so no `Runtime →
Agent/Workflow/Skill` dependency can arise."*

[E] **No twelfth boundary is available.** Blueprint §4: the core region
*"contains exactly the eleven frozen subsystem boundaries — no more."*

[E] **No precedent exists.** No boundary realizes `ExecutionConsumer` anywhere.

## 4. Decision

```
Residency of a concrete ExecutionConsumer:  the Agent boundary — UNIQUELY.
```

[A] It is not a preference among alternatives. It is the only residency the
permission graph admits.

## 5. Consequence — the block is not residency

[A] `ACT-CC-P6-039` established that the Agent boundary constrains a concrete
`participate()` to accepting its parameter and returning `None`: one
cross-boundary import fixed by equality, `Execution` unimportable, the
identifier `runtime` forbidden, and the halt-site count pinned at 12.

[A] Combining that with §4: **the only available residency is the one that
reduces E-01 to Option C.** Therefore:

> **Option B is not merely unattempted — it is proven impossible. No alternative
> residency exists.**

[A] `DEC-P6-035`'s governing principle — *"move the semantic consumer to the
architecture location where it legitimately belongs"* — has been tested against
the whole architecture. The consumer already belongs where it cannot work.

## 6. Alternatives considered and rejected on evidence

| Alternative | Rejected because |
|---|---|
| **Residency in `runtime/execution/`**, beside `consumer.py`, following the `contract.py`/`session.py` pairing | **Built and tested.** Failed `test_runtime_never_learns_of_a_consumer`. The assertion is broader than a `Runtime → Agent` ban: it forbids Runtime importing the *contract* at all. Module removed |
| **Residency in `workflow/` or `skill/`** — both named consumers in `consumer.py` | Neither may import `runtime`. Semantics also wrong: a generic participant is neither a governed composition nor a facility |
| **Widen `Execution` with a hosting-check verb**, letting a thin Agent-boundary consumer delegate | Would satisfy all four Agent constraints — but contradicts `agent_execution_semantics_spec.md §17.2`, written under authorized scope and ratified through `DEC-P6-033`'s reconciliation: *"Specifying preconditions does not authorize adding a precondition check."* Rejected on the specification's own terms |
| **A twelfth boundary** | Blueprint §4; expressly reserved by `DEC-P6-035` §7 |

## 7. What this decision does not do

[A] It relaxes no Agent assertion, reverses no protected dependency direction,
adds no export, and constructs nothing. The conformance suites are unmodified
and the repository is green at 616 OK.

## 8. Consequent Founder decision

[D] With Option B proven impossible, the choice `DEC-P6-035` framed collapses to
two, and both are Founder-reserved:

| | Option | Nature |
|---|---|---|
| **A** | Relax specific Agent-boundary assertions — most narrowly, the halt-site count and the `runtime` identifier ban — so a realization can validate and reach its host | Changes assertions `DEC-P6-029` issuance 3, `DEC-P6-032` and `DEC-P6-033` protect |
| **C** | Accept a semantically trivial E-01 | Available now; `DEC-P6-035` §10 currently records it as NOT SELECTED |

[A] A third path exists and is not a workaround: **authorize the consumer
phase.** `agent.py`, `consumer.py` and `execution/contract.py` each say
implementations arrive with *"future authorized consumer phases"*, and for Agent
that phase is the Agent Factory — reserved under `P7-L-1`. The architecture is
not missing a location; it is waiting on a phase that has never been authorized.
That is the deepest reading of the evidence, and it is offered as analysis, not
as a decision.
