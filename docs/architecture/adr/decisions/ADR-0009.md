## Problem Statement

A conformance regime that can say only *zero* or *one frozen exception* cannot
say **which** exceptions it tolerates, or **how many**.

The concrete consequence is present in the repository today. The
`expectedFailure` marker at `test_knowledge_conformance.py:358` asserts that the
test fails. It does not assert *why*, or *where*, or *how widely*. If a sixth
raise site acquired the same defect tomorrow, the test would still fail, the
marker would still be satisfied, and the suite would still report green. The
control cannot distinguish five sites from six, and it cannot distinguish a
defect that was **moved** from one that was **fixed**.

The gap is therefore not that AIOS tolerates a known defect — that tolerance is
governed and recorded. The gap is that **the tolerance is unbounded in extent
while appearing bounded in form.**

The mechanism AIOS lacks is one that can state: *these specific sites, and no
others.*

---

## Decision

Establish the **Bounded Exception Register** as the AIOS mechanism for recording
and enforcing bounded conformance exceptions.

### 1. The register is an allowlist of identities, never a count

Each entry names a specific exception site — file and locator — together with
the **Finding ID** and the **Governance Decision ID** that govern it. The
register's unit is identity, not quantity.

This is the decisive divergence from the external pattern that prompted it. A
count-based budget cannot tell a moved violation from a repaired one; an
identity-based allowlist can, because it names what it permits.

### 2. Enforcement is fail-closed in both directions

The verifier fails when:

- an exception site appears that the register does not name (**introduction**);
- the register names a site that no longer exists (**staleness**).

The second direction matters as much as the first. An allowlist that only
catches additions decays silently as its entries go stale, and a decayed
allowlist permits whatever its dead entries once described.

### 3. The register may shrink freely and grow only by Architect act

Removing an entry — because the underlying defect was repaired — requires no
governance act beyond the authorization that repaired it. **Adding** an entry
requires an explicit Architect act recorded in the Governance Decision Register.

### 4. There is no self-service expansion

The mechanism shall carry **no** `--update`, `--fix`, `--accept`, or equivalent
affordance capable of rewriting the register from the current state of the tree.

This is the property that separates a governed register from a ratchet. An
escape hatch usable by the party that introduced a regression relocates the
mechanism's integrity from structure to convention, and convention is verified
by nothing. GDR-0012 states the requirement directly: *"no self-service baseline
expansion."*

### 5. The register is append-only in governance, not in content

The file may shrink. Its **governance history** may not be rewritten: each entry
traces to the Finding and Governance Decision that admitted it, and that
provenance survives the entry's removal.

### 6. Relationship to conformance verification

The register does not replace conformance gates and does not weaken them. A gate
still passes or fails. The register narrows what a gate is permitted to tolerate,
converting an unbounded exception into an enumerated one. A boundary with no
registered exceptions is verified exactly as it is today.

### 7. What this decision does not decide

This ADR fixes the **architectural convention**. It does not fix the file
format, the serialization, the verifier's invocation, the locator syntax, or the
directory layout. Those are implementation concerns belonging to MB-01 Stage 2,
constrained by — not determined by — this decision.

## Alternatives Considered

**A — Retain the status quo (`expectedFailure` per finding).** Rejected. It is
the mechanism whose limitation created this problem: it cannot distinguish five
sites from six, and it silently absorbs new instances of a recorded defect.

**B — Adopt the external ratcheting budget directly (count-based, with
`--update`).** Rejected, and already rejected by GDR-0012: *"AIOS must not copy
jcode's mutable ratchet model directly."* Its unit is a count (EAI-0001 evidence
E-9: `total = 3243`, per-file counts, no site identities), and its `--update`
flag (E-8) is exactly the self-service expansion GDR-0012 forbids.

**C — Zero tolerance: forbid the defect class outright and repair every
instance.** Considered seriously, since EAI-0002 demonstrates it working in
practice (EP-6, RK-10). Rejected as the general mechanism for two reasons.
First, GDR-0012 accepted EP-1 precisely for cases where *"immediate elimination
is impractical"*, and repairing P7-F-2 requires modifying a frozen baseline
under a separate Maintenance Baseline — the impracticality is structural, not
preferential. Second, GDR-0013 decided EP-6 **REJECT AS GOVERNANCE MECHANISM**,
and RK-10 is explicitly non-authoritative. Where a defect class *can* be driven
to zero, zero remains the better answer, and this ADR does not license
registering an exception that could simply be fixed.

**D — Bespoke per-boundary suppression conventions.** Rejected. It produces no
cross-boundary consistency, no common governance trace, and no single place to
read what AIOS currently tolerates — reproducing the present problem eleven
times.
