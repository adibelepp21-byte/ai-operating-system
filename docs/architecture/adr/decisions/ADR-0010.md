# ADR-0010

## Metadata

- **Identifier:** ADR-0010
- **Title:** Reconcile the Canonical Domain Model's organizational-unit
  terminology with Founder decision FD-6 (Platform Division), by bounded
  amendment rather than global migration
- **Status:** **Approved**
- **Decision Owner:** Architect (Founder)
- **Proposer:** Claude Code / Co-Founder (Construction Phase)
- **Approval Record:** Executed under Founder authorization **ACT-CC-F03-009**
  and **ACT-CC-F03-010**, implementing Founder decision **FD-6** as recorded in
  **GDR-0020**.

This document records an **approved** architectural-tier decision under
Engineering Constitution §3.4. It reconciles a terminology inconsistency already
identified and already decided by the Founder. **It creates no new authority, it
decides no Founder-reserved question, and it authorizes no implementation beyond
the bounded amendment specified in Scope.**

---

## Context

### The governance state this decision enters

`ACT-CC-VAL-001` finding **F-09** recorded a vocabulary divergence: the frozen
Canonical Domain Model uses **Department** as its organizational-unit entity,
while the term occurs **zero times** across all 45 Volume 1 bodies. The Founder
resolved the underlying question:

> **FD-6 = OPTION A — PLATFORM DIVISION IS THE CANONICAL ORGANIZATIONAL UNIT**

recorded verbatim in **GDR-0020**.

`GDR-0020` deliberately left the Domain Model unamended and constrained how the
amendment may be made. Two constraints govern this ADR:

- **§3 Scope boundary** — the decision does *not* authorize *"renaming every
  occurrence of 'Department', global search-and-replace, alteration of
  historical evidence."*
- **§4 ADR route** — *"Amending `INV-1` / `INV-2` terminology requires **ADR-0010
  through a separate execution Act**, which this entry does not authorize and
  does not pre-approve."*

That execution Act is `ACT-CC-F03-009`, reaffirmed and bounded by
`ACT-CC-F03-010` Phase C.

### Why the inconsistency blocks work

The unresolved condition is tracked as blocker **B-07**. It is a
**Cross-Part Consistency** and **Terminology Integrity** defect: the canonical
semantic foundation names its organizational unit differently from the
architecture corpora built on top of it. The now-resident Volume 2 / PD-02
corpus uses **Platform Division** in **36 of its 50 bodies**, against **zero**
occurrences in the Domain Model.

---

## Problem Statement

The Canonical Domain Model defines the organizational unit as **Department**
(24 occurrences, including invariants INV-1 and INV-2). Founder decision FD-6
established **Platform Division** as the canonical organizational unit. The
Domain Model has not been amended, so the canonical semantic foundation
contradicts the canonical governance decision.

Three resolution paths exist:

1. **Global migration** — replace all 24 occurrences. **Excluded by
   `GDR-0020 §3`**, and it would erase the historical readability of prior
   records.
2. **Invariants only** — amend INV-1 and INV-2 alone. **Structurally invalid**:
   the invariants would reference an entity that the entity table does not
   define, creating a dangling reference.
3. **Bounded definitional amendment** — amend the *definitional* locations
   (entity list, entity definition, INV-1, INV-2) and record an explicit alias
   rule covering the remaining descriptive occurrences.

Path 3 is the only one that is both authorized and structurally coherent.

---

## Decision

**The canonical organizational-unit entity of the AIOS Domain Model is
`Platform Division`.**

**`Department` is its recorded historical alias.** Where `Department` appears in
the Domain Model's descriptive prose, in historical Acts, in prior Governance
Decision Register entries, in findings, in review reports, in commit history, or
in any other append-only governance evidence, it denotes the same entity and is
**historical terminology, not current canonical terminology**.

The amendment is applied **only** to the four definitional locations listed under
Scope, plus one explicit terminology note recording this alias rule. **No global
terminology migration is performed.**

---

## Scope

Exactly one file may change, at exactly these locations:

| # | File | Location | Change |
|---|---|---|---|
| 1 | `docs/architecture/domain-model/canonical-domain-model-v1.md` | §1 entity category table, `Spine` row | `Department` → `Platform Division` |
| 2 | same | §2 entity definition table, entity row | `**Department**` → `**Platform Division**`, with the historical alias recorded inline |
| 3 | same | §7 **INV-1** | `Department` → `Platform Division` |
| 4 | same | §7 **INV-2** | `Department` → `Platform Division` |
| 5 | same | §2, immediately after the entity definition table | **New** terminology note recording this ADR's alias rule |

Nothing else in the repository may change under this ADR.

---

## Non-Scope

The following **MUST NOT** change, and did not change:

- **Historical evidence of every kind** — historical Acts, prior GDR entries,
  prior findings, prior review reports, historical decision records, historical
  execution evidence, provenance records, and commit history. The presence of
  `Department` in a historical record does **not** authorize altering that
  record.
- **The remaining descriptive `Department` occurrences** in the Domain Model
  (relationship lists, ownership table, lifecycle notes, dependency rules,
  cost-management note). These are covered by the alias rule, not rewritten.
- **Unrelated entities** — Organization, Capability, Agent Definition, Agent
  Instance, Skill, Workflow, Tool, Runtime, Knowledge, Memory, Trace.
- **Unrelated invariants** — INV-3 through INV-12, including INV-10's
  `Cross-Department Capability dependencies` clause.
- **Unrelated authority relationships**, domain semantics, and any content
  outside the identified B-07 inconsistency.
- **Volume 1 and Volume 2 corpora**, the Engineering Constitution, the
  Architecture Freeze, and the Finding Register.

---

## Migration / Alias Treatment

No migration is performed. The alias rule is the migration strategy:

```text
CURRENT CANONICAL TERM      Platform Division
        ≠
HISTORICAL EVIDENCE         Department  (same entity, historical terminology)
```

This distinction is recorded explicitly in the Domain Model itself, so that a
remaining `Department` occurrence is never silently read as current canonical
terminology. Future documents use `Platform Division`. Historical documents
remain exactly as written and remain readable through this ADR.

---

## Alternatives Considered

| Alternative | Why rejected |
|---|---|
| Global search-and-replace across all 24 occurrences | Explicitly excluded by `GDR-0020 §3`; destroys historical readability; exceeds granted authority |
| Amend INV-1 / INV-2 only | Leaves the invariants referencing an entity the table does not define — a dangling reference and a new inconsistency |
| Record an external equivalence map, leaving the Domain Model untouched | Leaves the canonical semantic foundation in direct contradiction with FD-6; B-07 would remain open |
| Defer to a future Volume-wide terminology programme | The blocker gates Phase D and the P7-I99 Volume 2 review now; deferral is not remediation |

---

## Consequences

**Positive.** B-07's definitional contradiction is resolved. The Domain Model's
canonical entity now agrees with FD-6 and with the Volume 2 corpus. Historical
records stay intact and readable. The change is four lines plus one note.

**Accepted cost.** The Domain Model temporarily contains both terms: `Platform
Division` in its definitional locations and `Department` in descriptive prose.
This is **intentional and recorded**, not an oversight. Removing the remainder
would require the global migration `GDR-0020 §3` excludes.

**Not addressed.** Terminology in Volume 1's 45 bodies (which use neither term),
`native_core/` code identifiers, engineering specs, and historical governance
artifacts. None is within B-07 or this ADR.
