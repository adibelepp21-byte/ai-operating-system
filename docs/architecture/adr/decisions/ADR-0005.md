## Context

Runtime is fully defined (§2), categorized under Execution (§3), related via §4 ("Runtime hosts Agent Instance"), and owned centrally alongside Skill and Tool (§5). It is entirely absent from the Lifecycle Rules table (§6), leaving no stated basis for how a Runtime instance is versioned, evolved, or retired. This absence currently blocks any future Runtime Framework from being fully documented.

## Decision

Runtime adopts the lifecycle governance pattern used by centrally-owned Execution-layer entities such as Skill and Tool: versioned independently; evolved through governed revisions; compatibility boundaries preserved where applicable; behavioral drift documented at change time.

This is **pattern adoption, not entity equivalence** — Runtime is not claimed to be identical to Skill or Tool. Lifecycle governance treatment is deliberately separated from any claim about Runtime's underlying architectural identity or nature.

**Mandatory guardrail, stated explicitly:** This decision establishes lifecycle governance only. It does not determine whether Runtime remains a standalone Domain Model entity or becomes an attribute in the future. That question (Domain Model §9) remains deferred pending future architectural evidence, and nothing in this ADR should be read as bearing on it.

## Alternatives Considered

1. **Define a Runtime-specific lifecycle**, distinct from the shared centrally-owned-entity pattern. *Benefits:* potentially more architecturally precise to Runtime's role as "the conceptual seam where model/infrastructure substitution occurs" (§2), possibly treating substitution as the primary lifecycle event rather than an interface-preserving version bump. *Risks:* larger act of original semantic authorship; elevated risk of drifting into Constitution §6.2 invariant 1 territory (embedding technology/infrastructure decisions) if the language isn't kept strictly abstract; more assertively tilts the §9 deferred question toward "permanent, independently-governed entity" than pattern adoption would. *Reason rejected:* not selected by the Architect.
2. **Leave unresolved.** *Benefits:* avoids any interaction with §9's deferred question entirely. *Risks:* perpetuates a structural incompleteness in ratified text and continues blocking Runtime Framework creation indefinitely. *Reason rejected:* not selected by the Architect.

## Consequences

### Positive Consequences
- Closes the only remaining table-completeness gap for Runtime (Ownership Rules already state "owned centrally"; Lifecycle Rules now follow).
- Adopts an already-ratified governance pattern rather than inventing new mechanics, while explicitly avoiding a claim of entity equivalence with Skill or Tool.
- Separates lifecycle governance from Runtime's identity question, preserving the §9 deferral cleanly.
- Unblocks eventual Runtime Framework creation.

### Negative Consequences
- The shared centrally-owned-entity pattern was designed around interface-preserving evolution of executable ability/integration points; applying it to Runtime, "the conceptual seam where substitution occurs," may still understate the architectural weight of a Runtime change relative to an ordinary Skill/Tool version change. This is accepted as a known trade-off of pattern adoption, not resolved by this ADR.

### Future Implications
- A future Runtime Framework may document versioning/compatibility mechanics in more operational detail, without altering the Domain Model content established here.
- Any future ADR addressing §9's entity-vs-attribute question must account for the lifecycle governance content this ADR establishes, but is not constrained by it beyond that.

## Domain Model Impact

- **Entities affected:** Runtime, directly. Skill/Tool affected only as the referenced governance pattern — their own §5/§6 entries are unchanged.
- **Relationships affected:** None. §4's "Runtime hosts Agent Instance" is unchanged.
- **Ownership impact:** None — Runtime's existing §5 "owned centrally" entry is unchanged.
- **Lifecycle impact:** §6 gains a new Runtime row, adopting the same governance pattern already applied to Skill and Tool (versioned independently; evolved through governed revisions; compatibility boundaries preserved where applicable; behavioral drift documented at change time), without asserting Runtime is identical to either.
- **Invariant impact — evaluated, not invented:** No new invariant is proposed. Skill/Tool, the pattern being adopted, carry no dedicated lifecycle-specific invariant in §7 beyond Tool-specific invariant 12 (not applicable to Runtime's own versioning). Consistency with the adopted pattern argues against inventing one here. This conclusion should be confirmed by the Architect.

## Non-Goals

This ADR does not:
- Define Runtime technology.
- Define infrastructure.
- Define vendors.
- Define deployment mechanisms.
- Resolve the Runtime entity-versus-attribute question (§9) — explicitly and deliberately deferred, per the mandatory guardrail above.
- Claim that Runtime is identical to, or functionally interchangeable with, Skill or Tool.
