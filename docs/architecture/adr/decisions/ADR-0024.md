## 1. Correction — [E]

`ACT-CC-P6-049` through `-051` returned **BLOCKED**, on the ground that reading
the catalog required *inventing* an extraction rule. **That was wrong, and it was
a false stop of exactly the kind `DEC-P6-041` §11 names.**

[E] The rule was not mine to invent. It is already established and shipped in
this repository, in two validators:

> `tools/validators/agent_integration.py`: *"a catalog artifact **'declares' a
> given Agent Definition as its invoker if it links to that Agent Definition's
> file anywhere in its body** — **the same heuristic `link_classifier.py`
> already uses** for its agent-definition-reference category."*

[E] `tools/validators/link_classifier.py` carries the classification directly:
a link whose target lies under `agent-definitions/` is an
`AGENT_DEFINITION_REFERENCE`, excluding `*-framework.md` and
`agent-definitions.md`.

[E] `agent_integration.py` also already records the limitation I treated as
novel: *"**No structured field distinguishes intent from incidental citation
yet**, the same limitation the Cross-Reference Validator already documents."*
Its docstring notes the Architect identified this class of gap by direct
inspection and that the validator exists to make it tool-detectable.

[A] So the absence of a ratified machine-readable field is a **known, documented
state the repository has already chosen how to work around** — not an open
governance question barring all tooling. Under `DEC-P6-041` §5 this is
**Category A, delegated ambiguity**, resolvable through *"existing patterns"*
and *"repository evidence"*. I had classified it Category C.

[A] The error was mine and it was methodological: I searched canon for a field,
found none, and stopped — without running §10's *"search for existing
implementations"* against the tooling that already reads these documents.
`ADR-0022` and `ADR-0023` remain accurate on what **canon** specifies; they were
wrong that nothing could be **built**.

## 2. What was built

`tools/runtime_catalog.py` — `host_declarations()` returns, per governed Runtime
entry:

```python
{"runtime_key": "runtime.<slug>", "definition_names": ["<Name>", ...]}
```

shaped for `DefinitionCatalog.from_records`. Measured against the real catalog:

```
runtime.batch-governance-review-substrate         -> ['Governance Artifact Integrity Agent']
runtime.interactive-governance-session-substrate  -> ['Governance Artifact Integrity Agent']
runtime.textual-reasoning-execution-substrate     -> ['Governance Artifact Integrity Agent']
```

### Two deliberate narrowings — [A]

1. **Only the ratified `## Hosted Relationship` section is read.** Runtime
   Framework §8 makes that section mandatory and §9 places `Hosts Agent
   Instance` in it, so the boundary is ratified structure rather than a guess.
   An ADR citation or Domain Model pointer elsewhere in the document cannot be
   mistaken for a hosting declaration.
2. **A Definition is identified by the `**Name:**` its own Metadata declares**,
   not by the link's display text. Identity comes from the document that owns
   it. This also retires the display-text heuristic `ACT-CC-P6-049` measured and
   correctly refused to persist.

[A] Both narrow the *"medium false-positive risk"* `agent_integration.py`
documents for the reverse direction. This reader is strictly more conservative
than the practice it reuses.

## 3. Authority — what this does NOT claim — [A]

[A] The module reports what governed documents record. **Whether a documented
hosting reference is *authoritative input to execution*, as opposed to
descriptive documentation, remains an open classification reserved to the
Architect.** Nothing here decides it, and `DEC-P6-041` §14 is explicit that
documentation records authority and never manufactures it.

[A] Concretely: `native_core` was **not modified**. The reader returns plain
mappings; no Native Core module consumes them in production code. A caller may
feed them to `DefinitionCatalog`; that a value can be read confers no authority
on it (`ADR-0022`).

[E] Nor does this touch authoring. Reading `catalog → records` implies no
authority to write `→ catalog`, which `ADR-0022` established rests with the
Architect by documentation change.

## 4. Placement — [A]

`tools/`, not `native_core/`. [A] Grounds: every existing catalog consumer lives
there; `native_core` must not depend on repository layout; and the module
imports **nothing** from `native_core`, preserving `ADR-0021`'s split —
representation in tooling, meaning in Runtime. [E] Pinned by
`test_the_reader_imports_nothing_from_the_native_core` (AST-checked).

[A] Rejected: placing it in `native_core` (couples the core to `docs/` layout and
would need `re`, outside the Runtime stdlib allowlist — the allowlist stays
untouched, per `ACT-CC-P6-048`'s reservation); adding it to `validators/` (it
reports records, not `Finding`s); modifying the governance documents to add a
structured field (Architect-reserved).

## 6. Findings

1. **[E] `DEC-P6-041` is the Autonomous Construction Mode decision**, not the
   Runtime Catalog Hosting Declaration Policy that `ACT-CC-P6-050/051` gated on.
   That identifier is now consumed; the hosting-declaration policy, if still
   wanted, needs `DEC-P6-042`. [A] It is **no longer blocking** — reading is
   delegated, as §1 establishes.
2. **[D] Architect-reserved and genuinely open:** the authority classification
   of the hosting reference (descriptive · advisory · authoritative) and whether
   a structured field should replace the link. Neither blocks tooling; both
   would be required before Runtime treats a declaration as execution authority.
3. **[A]** `ADR-0021`'s Infrastructure decoding seam remains correct and generic.
   It decodes *stored* records; this reader produces records from *documents*.
   Both feed the same `from_records` seam. **No rework, and no conflict.**
