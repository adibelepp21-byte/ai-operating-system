## 8. Architecture Observations

**[A]** unless marked otherwise.

- **O-1** The declared allowlist (F-1) is structurally identical in *intent* to AIOS's dependency policy, but is enforced by **nothing** — no lint rule (F-4), no test (F-5), no CI step (F-7).
- **O-2 [E→A] Documentation contradicts implementation.** F-2 names `cli.entrypoints` as the sole exception; F-3 shows the actual and only edge is `cli/commands.py`. The policy's own escape clause points at the wrong module. Disclosed explicitly per the evidence-discipline rule.
- **O-3** That divergence is the predicted failure mode of O-1: an unenforced allowlist drifts, and it has drifted precisely at the single point where the architecture granted itself an exception.
- **O-4** F-6 is a **zero-tolerance suppression ban** — the exact architectural inverse of EAI-0001's ratcheting quality budget. Two external references, opposite answers to the same question.
- **O-5** The Protocol seam (F-8) buys no dependency inversion in practice: `providers` imports `application` 23 times regardless (F-9). Structural typing also means nothing verifies that a provider satisfies the port until a type-check or a runtime call.
- **O-6** `runtime` is a genuine **process composition root** — dependency-terminal, importing all eight peers, imported by exactly one.
- **O-7** F-10 attempts to bind documentation freshness to code change by convention. O-2 is direct evidence that it did not hold.

**EP-5 — REJECT.** Redundant: AIOS already holds the same allowlist concept and *enforces* it. Adopting the prose form would be a strict weakening. **[A]** Its real value is as a **counterexample** — O-2 is direct evidence of what an unenforced allowlist costs, with drift arriving first at the documented exception. **EP-6 — REJECT.** Inapplicable as a mechanism: AIOS runs no type checker, so a `# type: ignore` ban has nothing to gate. **[A]** It is nonetheless the most architecturally interesting finding of the review, because it is the **direct inverse of EAI-0001's EP-1**, approved as ADAPT. Same problem — accumulated exceptions — opposite answers: *tolerate a bounded, recorded set* versus *tolerate none and fix the cause*. Neither external reference is authoritative for AIOS.

**EP-7 — REJECT.** AIOS's nominal ABC contracts are strictly stronger under fail-closed discipline, and F-9 shows the Protocol did not deliver the dependency inversion it appears to promise.

**EP-8 — OBSERVE.** **[E] Compatibility UNVERIFIED.** AIOS Native Core is explicitly *"not a feature-complete runtime"* (GDR-0011 §3.11.1); there is no process-composition layer to compare against, so no evaluation can complete on evidence. **[A]** The question — whether one package may be permitted to know everything, and whether that privilege is bounded by structure or by convention — becomes live only when AIOS builds a runtime host.

**EP-9 — REJECT.** Redundant against AIOS's append-only registers with per-append integrity verification, and O-2 is direct evidence that the convention-only form fails.

## 14. What This Reference Means for AIOS Architecture

1. **What did the external system do?** Built a 254-module, nine-package multi-provider agent gateway with a clean layered dependency graph, two true dependency sinks, a declared least-privilege allowlist, and a zero-tolerance suppression gate.

2. **Why does it matter?** It supplies a live counterexample — an allowlist identical in intent to AIOS's, enforced by prose alone, already drifted at its own exception — and a suppression philosophy directly opposite to the one AIOS approved as ADAPT in GDR-0012.

3. **What is different in AIOS?** Every comparable control is enforced rather than declared: import-statement-granular allowlists, nominal fail-closed contracts, append-only records with integrity verification, and INV-12 and INV-13 as structure rather than policy.

4. **What, if anything, should AIOS change?** **Nothing.** No ADOPT, no ADAPT. One question (EP-8) is deferred until a process layer exists, and one piece of Reference Knowledge (RK-10) may inform — never decide — the design of the already-approved Bounded Exception Register when it reaches a Maintenance Baseline.
